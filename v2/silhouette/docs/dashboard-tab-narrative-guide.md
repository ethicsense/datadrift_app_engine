# 대시보드 탭 서사 가이드라인

날짜: 2026-04-25

단일 참조 문서. 새 탭을 만들거나 기존 탭 카피·레이아웃을 손볼 때 이 문서의 **질문 축**, **레이아웃**, **기술 탭 변형**을 먼저 확인한다.

---

## 1. 목적

- 탭마다 톤·상단 구조가 갈라지지 않게 한다.
- “스토리텔링”은 **과장된 문학**이 아니라, 사용자가 **무엇을 보고 있는지**를 한 번에 잡게 하는 질문·한 줄 설명·짧은 본문을 뜻한다.
- 기술 비중이 큰 탭도 같은 **뼈대**를 쓰되, 표·용어는 정확성을 우선한다(§5).

---

## 2. 질문 축(탭 유형)

각 탭은 **한 가지 질문**에 답하도록 상단을 맞춘다. 새 탭은 표에 행을 추가한다.

| 탭(예) | 질문 축 | 상단이 답해야 할 것 |
|--------|---------|---------------------|
| 개요 | 무엇을 다루는가, 범위는 어디까지인가 | 관측 범위·요약 지표 |
| 섬네일 | 무엇을 가져와 담았는가 | 수집 대상·원천·기록 단위·포함 필드 |
| 스키마 탐색 | **how** — 어떻게 정의·수집했는가 | raw/정규화, 필드 정의, 데이터셋 간 차이 |
| 가격 | 어느 가격대가 적절할까 | 구간별 분포, 할인·순위, 시간 변화, 상품 유형 교차 |
| 모멘텀 | 어떤 제품이 올라오고 꺾이나 | 순위 속도·가속·안정성, 세그먼트별 기세, 상위 사례·궤적 |
| 상품 정보 | 상품은 어떤 속성으로 채워져 있나 | 속성 보존 범위, 색/소재/원산지/지역 분포, 소재-가격대 교차, 사례 검증 |
| 카테고리 | 품목과 순위는 어떻게 연결되나 | 카테고리별 평균 순위, 점유율/모멘텀 동시 비교, 속성·가격대 교차, 시계열 변화 |
| 텍스트 | 사용자 반응 신호는 무엇을 말하나 | 감성/불만/사이즈·상황 신호, 문장 근거, 트렌드·브랜드 해석( OCR은 보조 ) |
| (추가) | 팀에서 정한 한 문장 질문 | … |

### 2.1 질문은 이렇게 정한다 (결정 요령)

중심 질문은 **위젯 목록이나 화면 구성에서 먼저 뽑지 않는다.** (모멘텀 탭에서 정리한 것과 같은 관점이다.)

1. **누가, 왜 이 탭을 여는가**  
   패션·커머스 **마케팅·기획 담당자** 입장에서, 이 화면을 열었을 때 **무엇이 궁금해서** 열었는지 한 문장으로 적어 본다.  
   - 예: 가격 탭은 “어느 가격대가 시장에서 통하는가”, 모멘텀 탭은 “지금 **누가 올라오고 꺾이는가**(순위 **움직임**)”처럼, **스냅샷 한 장**이 아니라 **의사결정·해석**에 가까운 호기심에서 출발한다.

2. **그 질문이 이 탭만의 일인가**  
   다른 탭(개요, 가격, 모멘텀 등)과 **겹치지 않는** 한 가지 축인지 확인한다. 겹치면 질문을 더 좁히거나, 탭 경계를 다시 정의한다.

3. **아래 차트·표가 그 질문에 답하는가**  
   대표 패널들을 나열했을 때 **설명 없이도** 그 질문에 닿는지 본다. 닿지 않으면 질문이 과하거나, 화면 구성이 질문과 어긋난 것이다.

4. **말투**  
   §4에 맞게 **직관·일상어**로 쓴다. 필요하면 질문형 대신 **짧은 진술형**도 가능하다(§2 규칙).

5. **표 §2에 고정**  
   확정한 한 문장(또는 동의어 1줄)을 표에 반영해, 이후 카피·히어로·3칸 카드가 모두 그 축을 따르도록 한다.

규칙: 히어로 제목(`h2`)은 가능하면 **질문형 또는 짧은 진술**로, `PageContainer`의 `description`은 **한 문장**으로 같은 축을 보조한다.

## 3. 공통 레이아웃

순서(위에서 아래):

1. `PageContainer` — `title`, `description`(한 줄).
2. `section.overview-story-hero` — `small`(영문 라벨 선택), `h2`, `p`(2~4문장 이하 권장).
3. `section.overview-story-grid`(선택) — 2~3개 `article.overview-story-card`로 한 단계만 요약(작성법은 §3.1).
4. 본문 — 기존 위젯, `SectionCard`, 표 등.

참고 구현: `apps/visualization-web/src/pages/OverviewPage.tsx`, `ThumbnailPage.tsx`, `PricePage.tsx`, `MomentumPage.tsx`.

### 3.1 히어로 바로 아래 3칸 카드 (`overview-story-grid`)

- **역할**: 이 탭이 보여 주는 내용 **전체**를 **세 갈래**로만 나눠, 아래 패널들을 **어떻게 묶어 읽으면 되는지** 안내한다. 단계별 사용법·위젯 ID 나열용이 아니다.
- **개수**: 기본 **3개** (`article.overview-story-card`).
- **작성법**(카드 하나당):
  - `span`: 그 축의 짧은 이름(예: 분포·구성, 성과·신호, 흐름·기준).
  - `strong`: 그 축을 한 줄로 **압축한 큰 제목**(과장 없이, 가독 위해 짧게).
  - `small`: 실제 차트·표와 **대응**되도록, 무엇을 묶어 보는지 **일상어**로 1~2문장.
- **정합**: 세 카드가 히어로의 중심 질문을 **대체하지 않고**, 질문에 대한 **읽는 축**만 나눈다. 기술 탭(§5)은 표·컬럼명·필드명은 그대로 두고, 히어로·3칸·위젯 카피만 이 톤을 따른다.
- **참고 예시**: `PricePage.tsx`의 가격·할인·유형 / 구간별 순위·변화량 / 시간축 변화 3축.

---

## 4. 카피 규칙

- 한국어, **직관·간결**. 같은 내용을 히어로·카드·`PageContextBar`에 반복하지 않는다.
- **제목·설명은 비전문·일상어를 우선한다.** `PageContainer`의 `title`·`description`, 히어로(`h2`, `p`), `overview-story-grid` 카드의 제목·부가 설명, 위젯/카드의 **사용자 대면** `title`·`description`·`takeaway` 등은 가능한 한 업계·분석 용어 없이, 처음 보는 사람에게 말하듯 짧게 쓴다. (데이터 표의 컬럼명·API 필드명은 §5 예외.)
- 채널·데이터셋 이름은 **하드코딩하지 않는다**. 필터에서 온 값을 요약해 쓴다(예: `parseSourceLabel` 패턴).
- “한 장·N개”처럼 **부자연스러운 단위 나열**은 피하고, 필요하면 도메인 용어(스냅샷, 관측 행)를 쓴다.

---

## 5. 기술 탭 변형

스키마 탐색 등 **완전 기술 맥락** 탭용:

- 서사(질문·짧은 설명)는 **히어로 + 보조 그리드**에만 둔다.
- **표·컬럼명·diff 결과**는 API·도메인 용어를 유지한다. 임의로 “예쁜 말”로 바꾸지 않는다. (§4의 일상어 원칙은 **서사 레이어**에 적용하고, 표 데이터 레이어와 혼동하지 않는다.)
- `SectionCard`의 `title`, `description`, `explainability`만 이 가이드 톤으로 **짧게** 다듬는다.
- 컨트롤(셀렉트 등)은 히어로 바로 아래 **한 줄 툴바** 또는 첫 `SectionCard` 상단에 둘 수 있다. `PageContextBar`로 상단을 다시 무겁게 만들지 않는다(§6).

---

## 6. 지양·정합

- **`PageContextBar`**: 개요·섬네일 정리 방향과 맞추어, 새 탭에서는 기본적으로 쓰지 않는다. 필터 맥락이 필요하면 한 줄 텍스트나 툴바로만.
- 히어로와 본문 **중복 설명** 금지.
- 로딩·빈 상태 문구도 같은 톤으로 유지한다.
